   **Смена архитектуры ядра. Subota 3.0 Core теперь строится на пяти столпах**:

   1. Изоляция через ModuleAPI и RestrictedProxy:
      - Принцип: Модуль при инициализации заявляет манифест (какие методы других модулей и какие ресурсы инфраструктуры ему нужны).
      - Реализация: ModuleAPI через RestrictedProxy создает для модуля «песочницу». Модуль видит только разрешенные методы. Если кто-то попытается вызвать self.interfaces.postgres_manager.drop_table(), а в манифесте был только fetch_all, система выдаст ошибку еще на этапе обращения.

   2. Динамическая инфраструктура (_infra_map)
      Ядро стало гибким в плане ресурсов синхронизации.
      - Регистратор: В ядре есть центральный реестр asyncio-объектов (Event, Queue, Lock).
      - Динамика: На основе конфига мостов ядро теперь автоматически создает пары ивентов *bridge_{Name}_initialized* и *bridge_{Name}_online*.
      - Связанность: Модули-потребители просто подписываются на эти ивенты по имени через ModuleAPI, не зная, как они созданы.

   3. «Умный» Конфиг (AppConfig на Pydantic v2)
      Конфигурация перестала быть просто словарем из YAML.
      - Оркестрация: Через model_validator(mode='after') ядро само синхронизирует зависимости. Ты правишь один мастер-список external_bridges, а данные сами разлетаются в Heartbeat, RemoteConfigManager и SystemStatus.
      - Валидация: Система не запустится, если в конфиге есть логическая ошибка (например, мост указан, а его настройки мониторинга — нет).

   4. Атомарность и надежность данных (Postgres Layer)
      - Уникальность: Введены UNIQUE CONSTRAINT на уровне БД.
      - Безопасность: Логика «проверь, потом запиши» заменена на атомарный INSERT ... ON CONFLICT DO NOTHING. Это исключает дублирование данных при перезапусках ядра или сбоях сети.
   
   - Как теперь выглядит цикл жизни системы:
      - Bootstrapping: Ядро читает YAML и через Pydantic строит полную карту зависимостей.
      - Infra Setup: На основе карты создаются все очереди и ивенты (включая динамические для мостов).
      - API Factory: Для каждого модуля создается свой экземпляр ModuleAPI.
      - Module Loading: Модули загружаются, получают свои «урезанные» интерфейсы и встают в режим ожидания сигналов (ready.wait()).

- 9.04.26:
 **MetricsArchiveModuel**
   Модуль предназначен для многоуровневой агрегации системных метрик (из таблицы system_metrics) в архивные таблицы разной гранулярности: дневные, недельные, месячные и годовые.
   
   1. Ключевые механизмы:
      - Идемпотентность и защита от гонок: Реализована через таблицу archive_metrics_log с уникальным индексом по типу архива и дате. Метод _try_mark_done гарантирует, что один и тот же период не будет обработан дважды разными процессами.
      - Обработка истории ("Нагонка"): При инициализации и запуске модуль находит самую раннюю запись в БД через _get_first_metric_date и последовательно обрабатывает все пропущенные дни до текущей даты.
      - Автоматизация: Модуль включает в себя планировщик _nightly_archive, который высчитывает время до следующего запуска (по умолчанию в 02:15 ночи) и уходит в режим ожидания.

   2. Логика обработки по источникам:
      - Модуль разделяет логику агрегации в зависимости от источника данных (source):
         - HealthChecker (Доступность сервисов):
            - Рассчитывает процент аптайма на основе строковых статусов online.
            - Агрегирует задержку (latency): вычисляет среднее, минимум и максимум.
            - При переходе от дня к неделе/месяцу используется взвешенное среднее (учитывается count_samples), чтобы избежать математических искажений.
         - TaskWatcher (Статус модулей):
            - Парсит сложные строки вида online 95.0% | Full-day | Other states: ....
            - Суммирует "тики" работы модулей относительно общего времени работы системы, определяя режим работы (Full-day или Part-time).
            - Сохраняет перечень побочных состояний (ошибок), возникших за период.
         - MetricsCollector (Ресурсы системы: CPU, RAM, Battery):
            - Числовые показатели: агрегируются через AVG, MIN, MAX.
            - Спец-логика для батареи: объединяет несколько метрик заряда в единый battery_summary и высчитывает средний процент работы от сети (Power Online).

   3. Иерархия данных:
      - Модуль реализует каскадную модель:
         - Daily: system_metrics (сырые данные) ➡️ metrics_daily.
         - Weekly: metrics_daily ➡️ metrics_weekly.
         - Monthly: metrics_daily ➡️ metrics_monthly.

   1. Назначение и Роль
      - Мост спроектирован как изолированный асинхронный сервис (Python/Docker), выполняющий роль «Дипломатического посредника» между внешней сетью (MQTT-устройства, MikroTik) и внутренней шиной данных Ядра (Redis).
      - Изоляция: Ядро не видит внешние устройства напрямую. Мост фильтрует, валидирует и перепаковывает данные.
      - Двойное гражданство: Мост одновременно является клиентом Redis (для связи с Ядром) и сервером/клиентом для полевых устройств (MQTT, RouterOS API).

   2. Механизм инициализации («Машинный Дух»)
      - Реализована многоступенчатая процедура безопасного запуска (Provisioning):
         - Генерация Nonce: При старте Мост генерирует уникальный одноразовый код (property_0).
         - Запрос конфигурации: Мост отправляет сигнал Ядру, прикладывая этот nonce.
         - Получение зашифрованного пакета: Ядро возвращает конфигурацию и ключ КМС, зашифрованные XOR-методом на базе этого nonce.
      - ConfigParser: Специализированный модуль Моста, который:
         - Ждет появления события в Redis.
         - Расшифровывает данные.
         - Валидирует их через Pydantic-модели (BridgeConfig).
         - Сигнализирует через asyncio.Event об успешной загрузке для запуска остальных подсистем.

   3. Система безопасности и криптография
      - В Мосту реализован собственный крипто-слой для защиты данных:
         - XOR-Шифрование: Используется для защиты транзитных данных (ключей и конфигов) между Ядром и Мостом. Метод основан на циклическом наложении SHA256-хеша ключа на байты данных.
         - Identity Verification (Проверка личности): Мост идентифицирует устройства по хешу аппаратных данных: SHA256(Android_ID + MAC). Реальные ID устройств в Мосту не хранятся в открытом виде.
         - HMAC-подпись: Для защиты от подмены данных устройствами реализована подпись пакетов.
         - Канонизация: Перед подписью JSON-пакет приводится к строгому виду (сортировка ключей, удаление пробелов), чтобы гарантировать идентичность хеша на обеих сторонах.
         - Signing Key: Ключ подписи динамически формируется из аппаратного хеша и nonce конкретного пакета.

   4. Внутренняя инфраструктура (Core Modules)
      - TaskWatcher (Супервайзер): 
         - Модуль мониторинга асинхронных задач. Следит за состоянием циклов (ConfigParser, MQTT loop), ведет счетчик перезапусков и обеспечивает «чистую» остановку сервиса.
      - BridgeRedisEventBus: 
         - Адаптированная шина событий, поддерживающая группы потребителей (Consumer Groups) и подтверждение обработки (Ack) для обеспечения надежности доставки сообщений от Ядра.
      - BridgeAPI:

   5. Протокол взаимодействия с устройствами (BasicNode)
      - Спроектирована базовая модель устройства (на примере Android-смартфона 2017+ года), работающая на Python (Kivy/Termux):
